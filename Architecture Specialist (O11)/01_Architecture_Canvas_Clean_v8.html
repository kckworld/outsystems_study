그림을 빠뜨리지 않고, 그림 속 박스 하나하나를 Layer/Sublayer 기준으로 연결해서 정리
이 문서의 공부 순서
  • 그림 1: Architecture Canvas Sublayers - 모듈을 어디에 배치할지 기준을 잡는다.
  • 그림 2: Identify Concepts 예시 - 업무 자료에서 어떤 concept를 찾아야 하는지 본다.
  • 그림 3: Architecture Iteration - concept 식별 → module 정의 → 검증/수정 반복으로 연결한다.
  • 시험에서는 "이 박스가 어느 Layer 인가?"와 "이 Dependency 가 맞는가?"로 자주 나온다.

0. 세 그림을 한 번에 연결해서 보기

이 단원은 그림을 따로따로 외우면 헷갈립니다. 반드시 아래 순서로 연결해서 봐야 합니다.

  1. 먼저 그림 2처럼 업무 자료에서 User process, Business concept, Utility/Integration concept를 식별한다.
  2. 그 다음 그림 1의 Architecture Canvas Sublayer 기준으로 각각을 어느 Layer에 둘지 정한다.
  3. 마지막으로 그림 3처럼 Define modules 후 Validate/Refactor를 반복한다.
시험 암기 문장
  • Identify concepts first, then define modules and place them in the correct layer.
  • Architecture design is an iterative process.
  • Dependencies should flow from End-user to Core to Foundation.

1. 그림 1 - The Architecture Canvas (sublayers)

※ Foundation Service (외부 서비스 wrap-up, NFR 지원, e.g. Audit trailing) / Library (Reusable libraries and plug-ins) 도 Foundation sublayers에 포함됩니다.

그림 1. Architecture Canvas Sublayers

이 그림은 Architecture Canvas를 3개 큰 Layer와 그 안의 Sublayer로 나눠서 보여줍니다. 시험에서는 단순히 이름을 외우는 것보다 "각 Sublayer의 책임이 무엇인지"가 중요합니다.

1-1. 큰 색상 구분

색상/영역큰 의미시험 판단 기준
파란색 영역User process / Frontend 쪽화면, 사용자 여정, 여러 front-end를 묶는 흐름
주황색 영역Core business 쪽업무 개념, 업무 엔터티, 업무 규칙, 업무 서비스
초록색 영역Foundation / 공통 기반 쪽비기능 요구사항, 외부 연계, 공통 UI, 라이브러리, 플러그인

1-2. Sublayer 별 상세 설명

Sublayer그림 속 설명시험식 해석
OrchestrationSeveral frontends를 mashup하여 unified UX 또는 cross-application workflow 제공여러 앱/화면을 묶는 상위 사용자 프로세스. 단순 Core Service가 아니다. 그림 주석의 (*)는 일부 버전 관련 주의 표시이므로, 시험에서는 "여러 front-end를 조정하는 사용자 흐름"으로 이해한다.
End-userFrontend User Interface modules사용자가 직접 보는 화면, UI Flow, User Journey. 재사용 서비스 제공자가 아니다.
CoreBusiness concepts around reusable servicesCustomer, Contract, Inventory 같은 업무 개념 중심 영역. 업무 엔터티와 업무 규칙을 담는다.
APICore Services를 외부에 노출하는 API 제공Core Service 자체가 아니라, Core를 외부/타시스템에 노출하는 통로.
Core WidgetsCore Widgets업무 개념에 묶인 재사용 UI 블록. 예: Customer selector, Product picker.
Composite logicBusiness Logic Composition 또는 Data Synchronize logic여러 Core Service를 조합하거나 데이터 동기화 로직을 담당. 단일 개념이면 Core Service, 여러 개념 조합이면 Composite logic 후보.
Core ServiceReusable Core Service업무 개념을 재사용 서비스로 제공. 예: Customer_CS, Contract_CS, Inventory_CS.
FoundationNFR 또는 Integration modules, any business context에서 재사용특정 업무에 묶이지 않는 공통 기반. NFR은 Non-Functional Requirement.
Style GuideReusable UI Patterns, themes, theme templates공통 Layout, Theme, UI Pattern. Customer 업무 규칙이 들어가면 안 됨.
Foundation ServiceExternal services wrap-up, NFR 지원 서비스 예: Audit trailERP/API/외부 서비스 연계, Auditing, Logging 같은 공통 서비스.
LibraryReusable libraries and plug-ins공통 라이브러리, 플러그인. 업무 개념이 아니라 기술 재사용 단위.
그림 1 시험 함정
• Customer 라는 업무 개념은 Foundation이 아니라 Core 후보이다.
• Common Layout은 화면에 보이지만 End-user가 아니라 Style Guide 후보이다.
• Auditing은 업무 데이터처럼 보여도 비기능 요구사항이므로 Foundation Service 후보이다.
• ERP는 외부 시스템이므로 End-user가 직접 호출하지 않고 Integration/Foundation Service가 감싼다.

2. 그림 2 - Identify Concepts 예시

그림 2. User processes / Business concepts / Utilities and integration

이 그림은 바로 모듈을 만든 결과가 아니라, "업무 자료에서 어떤 concept 후보를 찾아냈는지"를 분류한 그림입니다. 여기서 찾은 항목들을 그림 1의 Sublayer에 배치해야 합니다.

2-1. 그림 속 박스별 Layer 후보

그림 속 그룹박스Layer/Sublayer 후보판단 이유
User processesCustomer ManagementEnd-user고객 업무를 수행하는 사용자 프로세스/화면 흐름이므로 UI/업무 처리 흐름 성격
User processesLoan HandlingEnd-user 또는 Orchestration대출 처리 사용자 프로세스. 여러 front-end/업무 흐름을 묶으면 Orchestration 후보
User processesProduct and Services MktEnd-user마케팅 업무 화면/사용자 여정 성격
Business conceptsInventoryCore / Core Service재고는 업무 개념. 엔터티, 규칙, CRUD가 Core에 속함
Business conceptsContractCore / Core Service계약은 업무 개념. 계약 데이터/규칙은 Core
Business conceptsCustomerCore / Core Service고객은 대표적인 업무 개념. 화면명이 아니라 데이터/규칙이면 Core
Utilities and integrationERPFoundation Service / Integration Service외부 시스템 연계. 직접 UI가 호출하지 않고 wrapper로 추상화
Utilities and integrationCommon LayoutStyle Guide공통 Layout/Theme/UI Pattern이므로 재사용 UI 기반
Utilities and integrationAuditingFoundation Service감사 추적은 비기능 요구사항. 특정 업무 Core가 아니라 공통 기반

2-2. 그림 2를 보고 바로 외울 공식

User processes는 보통 End-user 쪽, Business concepts는 Core 쪽, Utilities and integration은 Foundation 쪽입니다.

핵심 공식
  • Management / Handling / Portal / Backoffice / Mkt = 사용자 프로세스 또는 화면 흐름 → End-user 후보
  • Customer / Contract / Inventory / Product / Order = 업무 개념 → Core 후보
  • ERP / Auditing / Logging / Common Layout / Theme / Plugin = 공통 기반 또는 외부 연계 → Foundation 후보

3. 그림 3 - Architecture Iteration

그림 3. Identify concepts → Define modules → Architecture Iteration

이 그림은 Architecture Canvas를 사용하는 과정입니다. 그림 2에서 concept를 식별하고, 그림 1의 Layer/Sublayer 기준으로 모듈을 정의한 뒤, 검증하고 다시 조정합니다.

3-1. 단계별 해석

단계영어한글 의미시험 포인트
1Identify concepts업무 개념을 식별한다화면부터 만들지 말고 concept를 먼저 찾는다
2Define modules개념을 모듈로 정의한다Layer/Sublayer에 맞게 모듈 책임을 나눈다
반복Architecture Iteration아키텍처 반복검증 후 문제 있으면 Refactor하고 다시 배치한다

3-2. 세 그림을 하나로 연결한 최종 흐름

아래 순서가 이 단원의 최종 이해입니다.

  1. 그림 2에서 Customer Management, Customer, ERP, Auditing 같은 concept 후보를 찾는다.
  2. 그림 1을 보고 각 concept를 End-user, Core, Foundation 및 Sublayer에 배치한다.
  3. 그림 3처럼 모듈 정의 후 dependency를 검증하고 필요하면 refactoring한다.
Dependency 기본 방향
  • End-user → Core → Foundation 방향이 기본이다.
  • Core → End-user는 화면 의존성이므로 위험하다.
  • Foundation → Core는 공통 기반이 업무 개념을 알아버리므로 위험하다.
  • End-user → End-user는 lifecycle 독립성을 깨뜨릴 수 있다.
